# NarrativeOS 剩余功能与验收路线

**文档目的：**列清从当前可运行基线到“NarrativeOS 可独立支撑长篇小说创作、`aitest` 不再需要”的剩余工作。本文把已经迁入的旧能力、尚待核对的兼容性、要新建的能力分开，避免把“代码已复制”误当成“产品已完成”。

## 2026-09-23 实施进度

本轮已经把 roadmap 的主要“设计项”推进为可运行、可测试代码：

- **P0 旧功能对照**：新增 `docs/compatibility-matrix.md`，覆盖作品、章节、编辑、版本、人物、世界观、AI、Provider、SQLite、响应式等旧能力；旧五表 SQLite 原地升级测试通过，正文、版本、人物、设定不会因升级丢失。
- **P1 工作流**：实现持久化 `WritingTask / AgentRun / ReviewFinding / Approval`，支持 Writer → 3 个独立 Reviewer → Revision → 人工确认；确认前不改正文，确认后新增章节版本；状态机阻止重复确认/未确认归档；Reviewer finding 可保存原文片段与字符位置，Agent Run 记录 prompt 版本与耗时。
- **P1 Memory Engine**：实现作品级结构化记忆、候选/确认状态、作品隔离、版本历史、恢复和已确认记忆冲突检测；只有已确认记忆进入 Agent 上下文。
- **P1 Skill Engine**：实现作品技能、启停、版本发布、版本历史与恢复；任务创建时可选择 Skill，并冻结当时版本；支持指定子集或明确不使用 Skill；每个 Agent Run 保存实际引用版本，后续规则升级不会改写历史任务解释。
- **P1 内容库连接**：新增 `NOVEL_CONTENT_ROOT` 与作品 slug 绑定、预检和资料导入；可把 project/world/character/outline Markdown 幂等导入 Memory、把 shared writing-style 导入 Skill；人工确认后归档 chapter/review/version，同步失败可独立重试。
- **P1 新 UI / 主题**：工作台新增 **墨白、深空、纸页、Neo Pop** 四套主题并本地持久化；任务、Memory、Skill、内容库绑定均有浏览器入口；移动端新增作品/章节抽屉，创作辅助区不再被隐藏。
- **P0 自动化验收**：GitHub Actions 当前 HEAD 已通过 Python compileall、Ruff、JavaScript 语法、pytest 和 Chromium Playwright 浏览器验收。浏览器用例覆盖主题持久化、正文自动保存刷新不丢、任务/Memory/Skill 入口、390px 移动端章节抽屉、移动端创作区可见、无横向溢出与无页面 JS 异常。
- **测试结果**：完整《零点站台》验收后的 CI Run #72：**18 passed，0 failed**（另有 1 条第三方弃用 warning），Python compileall、Ruff、JavaScript 语法、Chromium Playwright 与 pytest 全部 success。完整正文验收发现并修复了一个 P0：Writer `continue` 输出曾可能在批准时覆盖整章；现在只会在保留原章基础上追加续写。

## 1. 旧功能对照与兼容验证（P0）

以 `docs/aitest-reference.md` 和源仓库当前版本为基准建立逐项矩阵，至少检查：

- 作品增删、切换、章节创建与删除、搜索和章节顺序。
- 正文输入、自动保存、快捷保存、保存状态与字数统计。
- 章节版本生成、历史查看、旧版本恢复，以及删除时的数据关联行为。
- 人物卡和世界观条目的新增、列表、作品隔离和数据格式。
- 续写、润色、一致性检查、自定义指令、结果预览、追加/替换正文。
- Demo fallback 提示、Provider 配置、环境变量引用、模型错误呈现。
- 首次启动数据库初始化、示例数据开关、数据库路径配置和已有 SQLite 数据兼容。
- 桌面与窄屏布局、关键交互、空状态、错误状态和页面刷新后的数据持久性。

每一项标注为“保持”“升级”“明确移除”，并给出对应文件、测试和理由。不得静默丢弃用户可见能力或已有数据；结构变化要提供可重复、可回滚的迁移步骤。

**验收：**矩阵无未归类功能；P0 行为有自动化测试；在使用旧数据库副本的升级演练中，记录数、正文、版本和关系均可核对。

## 2. NarrativeOS 界面与可切换整体主题（P1）

旧版工作台作为功能基线，界面升级需要表现平台的真实工作结构：作品/章节、创作任务、Writer、Reviewer、记忆、技能、版本与运行记录。主题只改变视觉 token 和呈现方式，不改变业务数据和页面路由。

建议首批主题方向：

1. **纸本文学**：暖纸色、墨色正文、轻量边栏，适合长时间阅读和写作。
2. **深夜书房**：低亮深色背景、暖色阅读区和克制高亮，适合夜间创作。
3. **创作控制台**：冷静的深浅中性色、任务/评审状态强调色，适合查看流程和审阅结果。

主题偏好保存到本地用户设置，提供全局切换入口；检查编辑器可读性、对比度、焦点态和手机宽度。可先实现基础版三主题，再按真实使用反馈打磨，不为主题引入不同业务行为。

**验收：**任意页面切换主题后路由、未保存内容和任务状态不丢；刷新后偏好保留；三个主题均完成桌面/移动和键盘可访问性检查。

## 3. Writer / Reviewer 工作流（P1）

以可恢复的任务执行器承载单 Writer、多 Reviewer 与修订循环，不把它做成仅能一次性调用模型的按钮。

最小流程：

1. 用户选择作品、章节/目标、写作任务、上下文和可用技能。
2. Writer 生成草稿并保存输入、模型、提示版本、输出和耗时。
3. 多个 Reviewer 独立检查剧情因果、人物连续性、设定一致性、节奏与语言。
4. 汇总意见，区分阻断项和建议项；Revision Agent 按选定意见修订。
5. 用户查看差异，选择接受、继续修改或退回；只有确认后才成为正式章节版本。
6. 记录每轮状态、失败、重试、模型输出和人工决策，支持中断后恢复。

数据对象至少包括：`WritingTask`、`AgentRun`、`ReviewFinding`、`Revision`、`Approval`。单 Agent 和多 Agent 共用 Provider 抽象；并行 Reviewer 可独立超时/失败，汇总阶段要显示缺失结果，不把失败伪装成通过。

**验收：**可在无真实 API Key 的 Demo 模式跑通全流程；任一阶段失败可重试且不覆盖原文；审阅问题可以定位到章节/文本片段；人工接受后产生新版本，历史可恢复。

## 4. Memory Engine（P1）

记忆是项目知识的结构化管理和检索层，不是将所有文本拼进提示词。至少支持世界规则、人物状态、时间线、地点/势力、道具、未解问题和已确认事实。

- 每条记忆带作品范围、来源、确认状态、创建/修改版本和关联章节/任务。
- Writer 与 Reviewer 按任务选择相关记忆并显示引用来源。
- 新草稿可以提出记忆候选更新，但不能无记录覆盖已确认设定。
- 发现人物、时间或规则冲突时生成可解释的冲突项，供用户确认处理。
- 提供检索、筛选、编辑、确认/撤销和影响范围查看。

**验收：**同名角色跨作品不串记忆；生成结果可追溯到引用的设定；冲突可复现并处理；错误更新可撤回；不依赖外部向量服务也能用 SQLite/关键词检索完成 MVP。

## 5. Skill Engine（P1）

技能用于可复用的写作与评审方法，区分平台内置技能、作品技能和用户私有技能。

- 技能包含名称、用途、输入约束、正文、版本、启停状态和适用 Agent/任务。
- 任务创建时可选技能；运行记录保存当次实际使用的技能版本。
- 评审与用户修订中总结出的经验先进入候选，不直接改写正式技能。
- 支持比较版本、发布、回滚、停用和查看被哪些任务使用。

**验收：**同一任务可复现当时技能版本；升级技能不会改变历史运行记录；候选经验需要审核后才能成为正式版本。

## 6. `slow-world-novel` 内容库连接与真实创作闭环（P1）

NarrativeOS 管理创作流程；`slow-world-novel` 保存小说正文、世界观、人物、章节、评审与版本归档。平台存储的项目记录应指向作品仓库中的项目目录，明确文件读写边界和失败恢复策略。

原计划首个验证项目使用《慢速世界》；按 2026-09-23 的产品决定，最终改用独立验收小说《零点站台》，避免对正式《慢速世界》正文做试验性写入。验收读取作品资料并完成一章任务，经过 Writer 草稿、多 Reviewer 审核、修订、人工确认，最终写入章节文件并保存评审记录和版本。重复执行不能覆盖已接受的章节；平台 SQLite 与 Git 内容库的状态不一致时提供清楚的恢复入口。

**验收：**完整跑通至少一章；章节、评审和版本在仓库中有清楚位置；重启平台后任务状态和数据库记录可恢复；用户能从章节追溯到对应任务和审阅意见。

## 7. 测试、可靠性与删除 `aitest` 的门槛（P0）

补齐以下测试：旧 API 行为回归、SQLite 初始化/迁移、Provider 配置与异常、多 Agent 部分失败/重试、章节版本恢复、浏览器核心流程、主题切换、作品数据隔离，以及真实章节端到端演练。CI 应安装固定范围依赖、运行 Python/前端静态检查与自动化测试，并保留清楚的失败日志。

当下列条件同时满足时，`aitest` 即“不再有用”，可删除：

1. 旧仓库可运行能力均完成有结果的对照，未保留未解释的差异。
2. NarrativeOS 在干净环境可独立安装启动，CI 与端到端测试通过。
3. 旧版数据兼容/迁移已演练，关键作品内容和版本可恢复。
4. 独立验收小说《零点站台》至少一章完整经过生成、审核、修订、确认和归档。
5. NarrativeOS 文档包含安装、配置、备份/恢复、故障排查；团队不再依赖旧仓库进行回退。

达到门槛后先确认 `aitest` 不再承担对照、恢复或运行职责，再执行删除；届时不删除 `slow-world-novel`，它是小说作品的独立归档库。

## 推荐实施顺序

1. 完成旧功能矩阵和数据升级演练，修复发现的 P0 遗漏。
2. 明确项目/章节/任务/记忆/技能数据模型与内容库读写契约。
3. 完成主题化工作台基础和 Writer → Reviewer → Revision → 人工确认的纵向切片。
4. 补全 Memory/Skill 管理与审计，再扩展多 Agent 错误恢复。
5. 在独立验收小说《零点站台》跑通一章，按实际问题修订产品和工作流。
6. 运行全套测试、CI 和备份恢复演练，确认旧仓库不再有用途后清理 `aitest`。

## 当前不纳入首期

多用户协同、复杂权限体系、云端向量数据库、自动发布到外部小说平台、无法回滚的自动学习。先让本地优先的单人创作闭环可靠，再根据真实使用决定扩展。
