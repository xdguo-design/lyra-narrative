# 《灰街》写作流水线速度问题复盘

日期：2026-10-05  
分支：dev  
适用范围：NarrativeOS / 《灰街》章节生产与审核流水线

## 1. 现象

在推进《灰街》第 4、5 节时，出现“20 多分钟仍未交付两节”的明显异常。

实测发现，问题不在单次正文生成本身，而在流水线存在重复审核、错误审核、无意义 CI 和串行等待。

## 2. 已确认根因

### 2.1 Gate 章节范围错配

第 2 节审核时，Reviewer 仍接收到第一节《怀表》的专属冻结目标 / 第一节执行锁，导致把第 2 节合法内容误判为越界。

典型误判包括：
- 要求第 2 节再次出现第一节雨天灰街开场；
- 要求第 2 节重新包含哈钦斯太太 / 鸦巷尸体；
- 把雷蒙德、十三号仓等第 2 节合法内容判成“第一节越界”。

后果：
- 同一份正文被重复 Gate；
- 产生假 FAIL；
- 每轮 8 路 Reviewer + 总编核验均重复消耗时间。

验证结果：
- 同一份第 2 节正文，一字未改；
- 修复 Gate 章节范围后，重新审核直接 PASS；
- 因此可确认此前部分 FAIL 为程序性误判，而非正文真实问题。

### 2.2 小说正文提交触发完整 CI

此前任何 push 到 dev，包括：
- books/**
- .github/requests/**

都会触发完整 CI。

完整 CI 包含：
- 安装 Python 依赖；
- 安装 Chromium / Playwright 系统依赖；
- compileall；
- Ruff；
- JS check；
- pytest；
- 浏览器测试。

正文改动并不需要运行整套程序测试，造成大量无意义等待。

### 2.3 写作与 Gate 串行

原执行方式接近：

第 4 节写完 → 等第 4 节 Gate → 看结果 → 再写第 5 节。

审核期间没有继续推进下一节，导致模型审核时间直接叠加到总生产时间。

现已改为：

第 N 节进入 Gate → 同时继续写第 N+1 节。

若某节 FAIL，只返修该节。

### 2.4 过度轮询 Actions 状态

执行过程中曾频繁查询 GitHub Actions 状态。

这不会让 GitHub Action 本身变慢，但会占用主控执行步骤，导致正文生成、返修、下一节推进被人为打断。

今后只在以下节点检查状态：
- Gate 预期完成窗口；
- 需要读取失败 artifact；
- 准备锁稿前；
- 用户主动询问实时状态。

## 3. 已实施修复

### 3.1 Gate 按章节裁剪规则

第 2～5 节不再接收：
- 第一节《怀表》冻结目标；
- 第一节执行锁；
- 第一节 Reviewer 误报边界。

Reviewer 必须使用当前章节计划中的章节目标。

若 Reviewer 使用其他章节专属规则判 FAIL，总编应视为 SCOPE_MISMATCH，不得据此要求正文返修。

### 3.2 增加章节范围回归测试

新增测试：
- 后续章节规则不得包含第一节专属锁；
- scoped Canon 对第 2 节及以后必须裁掉第一节专属冻结段；
- 第 1 节仍保留完整第一节规则。

### 3.3 CI 拆分

普通 CI：
- 适用于程序 / 脚本；
- compile app、tests、scripts；
- Ruff；
- JS check；
- pytest（跳过 browser suite）。

Browser CI：
- 仅当 app/**、tests/test_browser.py、requirements 等 UI / 浏览器相关内容变化时运行；
- 单独安装 Chromium；
- 单独运行 browser tests。

纯小说内容和运行请求：
- books/**
- .github/requests/**
- artifacts/**

不再触发整套程序 CI。

### 3.4 Gate 快路径

8 路 Reviewer 全部 PASS 且静态 Gate PASS 时：
- 不再额外调用第 9 个总编模型。

只有出现：
- FAIL；
- ERROR；
- 静态 Gate 失败；

才调用总编模型核对证据和误判。

## 4. 实测时间

修复前的完整短链路：
- Writer → 8 路审核 → 修订
- 约 4 分 40 秒～5 分 10 秒 / 节。

单独 Gate：
- 约 1 分 15 秒～1 分 40 秒 / 轮。

修复后的实际记录：
- 第 2 节 scoped Gate：约 89 秒，PASS；
- 第 3 节 scoped Gate：约 88 秒，PASS；
- 第 4 节 Gate：约 89 秒，FAIL；
- 第 5 节 Gate：约 98 秒，FAIL。

合理目标：
- 一次通过：约 3～5 分钟 / 节；
- 需要一次返修：约 5～8 分钟 / 节。

若一节超过约 5 分钟仍没有候选稿 + 首轮 Gate 结果，应先检查流水线，而不是继续等待。

## 5. 后续硬规则

1. 同一节原则上只允许先跑 1 次正式 Gate。
2. 第 2 次仍 FAIL 时，先检查：
   - Gate 是否加载了错误章节规则；
   - Canon 是否污染；
   - Reviewer 是否误判；
   - artifact 是否对应当前候选稿。
3. 未确认程序正确前，不得连续触发第 3、第 4 轮 Gate。
4. Gate 运行期间必须并行推进下一节，不得空等。
5. 纯正文提交不得触发完整程序 CI。
6. 真正硬伤才返修正文；SCOPE_MISMATCH、无证据误判、重复审美意见不得造成整章重写。
7. 角色 1（创作总控）PASS 后，只代表单章可锁定。
8. 每完成 5 节 / 阶段节点，必须由角色 2（最终连续阅读者）从头连续阅读；角色 2 FAIL，整批打回。
9. 角色 1 PASS + 角色 2 PASS 才可视为正式交付。
10. “三节内进入正题”作为节奏硬规则：第 1 节建立异常，第 2 节形成期限/竞争压力，第 3 节必须出现不可逆主线冲突；否则角色 1 直接 FAIL。

## 6. 当前《灰街》状态（记录时）

- 第 1 节：PASS，已锁稿。
- 第 2 节：PASS，已锁稿。
- 第 3 节：PASS，已锁稿。
- 第 4 节：候选稿完成，Gate FAIL，待针对真实硬伤返修。
- 第 5 节：候选稿完成，Gate FAIL，待针对真实硬伤返修。
- 角色 2 连续阅读：需等第 4、5 节角色 1 PASS 后再执行。

## 7. 结论

本次速度异常主要来自流水线自身：
- 错误章节规则导致假 FAIL；
- 正文改动触发无意义完整 CI；
- 写作与审核串行；
- 状态轮询过密。

这些程序性问题已完成修复与验证。

后续如果再次出现“一节明显超过正常生产时间”，优先检查流水线，不允许把程序问题误当成正文质量问题反复重写。
